Project Vision

We are not building a simple chatbot.

We are building a:

Tool-augmented SLM coding assistant
strengthened by specialized DL advisors,
controlled by a Python orchestrator,
protected by rules,
verified by tests,
and improved through trace memory.

The main principle:

The SLM thinks.
The DL advisors guide.
The orchestrator governs.
The tools act.
The validators prove.
The traces teach.

But the real control flow should be:

1. User gives request.
2. Orchestrator creates TaskState.
3. Advisors analyze the request.
4. SLM receives structured context.
5. SLM proposes next action.
6. Tool router validates the action.
7. Tool executes.
8. Validator checks result.
9. TaskState updates.
10. Loop continues until solved or stopped.
11. Final answer is generated only from verified evidence.

C. Orchestrator

This is the most important part.

The orchestrator is the governor of the whole system.

It does not “think like an LLM.” It coordinates.

Responsibilities
Create TaskState
Call advisors
Call the SLM
Validate SLM tool requests
Execute tools through router
Update state
Stop infinite loops
Trigger validators
Save traces
Decide when task is complete
Technology

Use:

Python
Pydantic models or dataclasses
asyncio later if needed
Important rule

The SLM must not directly execute anything.

The SLM only says:

{
  "action": "read_file",
  "args": {
    "path": "app/main.py"
  },
  "reason": "Need to inspect the FastAPI route."
}

Then the orchestrator decides whether this is allowed.

D. TaskState

TaskState is the shared memory of the current task.

It prevents the system from becoming random.

Example
from dataclasses import dataclass, field
from typing import Any


@dataclass
class TaskState:
    task_id: str
    goal: str
    workspace: str

    intent: str | None = None
    status: str = "running"

    advisor_outputs: dict[str, Any] = field(default_factory=dict)
    evidence: list[dict[str, Any]] = field(default_factory=list)
    candidate_files: list[str] = field(default_factory=list)
    tool_history: list[dict[str, Any]] = field(default_factory=list)

    proposed_patch: dict[str, Any] | None = None

    validation: dict[str, Any] = field(default_factory=lambda: {
        "syntax": None,
        "tests": None,
        "patch_scope": None,
        "risk": None,
    })

    final_response: str | None = None
Responsibilities
Store goal
Store evidence
Store files inspected
Store advisor results
Store tool history
Store proposed patch
Store validation results
Store final answer

This will also become training data later.

3. SLM Core

The SLM is the central reasoning component.

It is not the boss. It is the main thinker.

Role of the SLM

The SLM should handle:

Planning
Reasoning
Choosing next suggested action
Explaining errors
Proposing small patches
Summarizing verified results
Converting technical evidence into clear answers
What the SLM should not control

The SLM should not directly:

Edit files
Run arbitrary commands
Delete files
Claim tests passed
Access files outside workspace
Bypass validators
Technology options

Since you already tested a fast SLM before, the likely setup is:

Ollama
local SLM
Python HTTP client
structured JSON prompting

Possible local SLM types:

Qwen2.5-Coder 1.5B
Qwen2.5-Coder 3B if your laptop handles it
Phi small models
Tiny code-focused models

For your RTX 3050 4GB VRAM, we stay realistic:

small quantized model
local inference
short structured prompts
tool-based context instead of huge context
Output format

The SLM must output structured JSON actions.

Example:

{
  "action": "run_tests",
  "reason": "The task asks to fix a failure, so tests must be run first.",
  "args": {
    "command": "python -m pytest"
  }
}

This makes the system controllable.

4. Specialized DL Advisor Layer

This is where your idea becomes strong.

The SLM is weak alone, so we surround it with specialized advisors.

Important:

Advisors guide.
They do not control.

Each advisor produces structured signals.

Advisor 1: Intent Classifier
Purpose

Understand what the user wants.

Input
User request
Output
{
  "label": "debug_error",
  "confidence": 0.94
}
Possible labels
debug_error
explain_code
generate_code
refactor_code
write_tests
setup_project
run_command_help
project_question
optimize_code
Technology

Start simple:

Rule-based keywords
then scikit-learn classifier
then small PyTorch model

Good MVP path:

Version 1: keyword/rule classifier
Version 2: TF-IDF + Logistic Regression
Version 3: small neural network

Do not train deep learning here on day one.

Advisor 2: File Relevance Ranker

Input

Advisor 4: Risk Scorer
Purpose

Estimate how dangerous a proposed patch is.

Input
patch diff
file path
number of lines changed
file type
test coverage
affected functions
Output
{
  "risk": "medium",
  "confidence": 0.76,
  "reason": "Patch changes API response schema."
}
Risk levels
low
medium
high
blocked
MVP rules
1–5 lines changed in normal source file → low
changes test + source → medium
changes config/auth/database → high
deletes files → blocked
touches secrets → blocked
Technology

Start with:

Python rules

Later:

RandomForest/XGBoost

Advisor 5: Patch-Quality Scorer
Purpose

Score whether a patch is likely to solve the problem.

Input

Output

  "quality_score": 0.82,
  "recommendation": "try_patch"
}
Important

This does not replace tests.

It only helps decide which patch to try first.

Truth still comes from validators.

Technology

Later only.

Do not build this in MVP.

Use trace data first.

Purpose

}

Purpose

6. Rules and Safety Policy

This is non-negotiable.

The assistant must be safe before it is smart.

File safety

Block:

.env
*.pem
*.key
secrets.*
credentials.*
password*
node_modules
.venv
.git
system folders
outside workspace
Command safety

Allow only whitelisted commands.

Start with:

python -m pytest
pytest
python -m compileall .

Block:

rm -rf
del /s
format
curl | bash
wget scripts
powershell destructive commands
registry edits
system package installs
Patch safety

Block or require approval for:

large diffs
file deletion
changes outside workspace
secret files
database migrations
auth/security code
package lock changes
7. Validator Layer

Validators establish truth.

Syntax validator

Checks:

Can Python parse the edited file?
Patch validator

Checks:

patch size
target path
old text match
risk level
forbidden files
Test validator

Checks:

Did tests pass?
Which tests failed?
Was exit code 0?
Result validator

Prevents false claims.

The assistant can only say:

Tests passed

if the test tool returned:

exit_code = 0

Use a tiny broken Python project.

def add(a: int, b: int) -> int:
    return a - b
test_calculator.py

    assert add(2, 3) == 5

Assistant does:

13. The Most Important Rule

Do not start by training models.

Start by building the system that produces useful data.

The correct order is:

Tools first.
Validation second.
SLM loop third.
Trace memory fourth.
Specialized ML/DL advisors fifth.

Because without traces, the specialized DL models will be weak guesses.

With traces, they become trained from real assistant behavior.

Final Direction

The project should be built as:

A small SLM strengthened by:
- structured planning
- specialized advisors
- safe tools
- AST code understanding
- test verification
- memory traces
- Python rules

This is strong, realistic, explainable, and much more impressive than a simple LLM wrapper.
